# log-insight 框架设计文档

> 版本: v1.0 (实现基线)
> 日期: 2026-10-20
> 状态: v0.3 已实现 —— 前端已基于 witty-log-analyzer (MulanPSL-2.0) 完成整体替换，全链路（认证 / 团队协作 / 日志解析 / 规则引擎 / 按需 LLM / 性能离线分析 / 智能诊断本地文件浏览 / 审计）已打通；智能诊断的对话与运行状态仍为前端演示数据

## 1. 项目概述

log-insight，Python 实现的 Web 运维平台：

- **部署环境**: Linux / Windows 均支持，ARM (aarch64) / x86 双架构
- **访问方式**: Web 端 (浏览器)
- **核心功能**:
  1. 用户权限控制：平台级 JWT + RBAC，叠加团队级双角色（管理员/普通用户，创建者与管理员权限合一）
  2. 团队协作：团队创建 / 申请加入 / 邀请审批 / 成员角色调整 / 任务与规则按团队隔离
  3. 故障诊断日志分析：6 种解析器插件 + 上传预检 + 服务端分页日志筛选
  4. 智能巡检：规则匹配打底 + 按需 LLM 智能总结（SSE 流式，可降级纯规则）
  5. 巡检规则管理：管理员对规则增删改查，规则热加载（免重启）
  6. 性能数据图表：服务端持久保存 + 降采样查询 + 视图配置落库
  7. 智能巡检规则推荐：LLM 分析日志后评估规则完善程度并推荐新增规则项，用户可编辑与一键接纳
  8. 性能离线分析：上传即解析的 sar / blktrace / netcap / 中断计数变化 可视化（结果不落库，仅本次展示）
  9. 智能诊断工作台：三栏（目录文件 / 文件阅读器 / 会话对话）；只读浏览后端主机真实磁盘（路径白名单）、勾选与拖拽入提问上下文、watchdog + SSE 变更实时刷新
- **用户规模**: ~1000 用户，每秒并发上传约 100+ 次，后续可能增长
- **日志来源**: 被动上传模式 —— 用户在目标服务器收集日志包后上传到平台分析

## 2. 总体架构

```
┌────────────────────────────────────────────────────────────┐
│   浏览器 (Vue3 + TS + Pinia, o-design 风格, SSE 客户端)      │
│   http.ts 深度 snake→camel · 401 刷新重放 · SSE ?token=     │
└───────┬──────────────────────────────┬─────────────────────┘
        │ 1. REST (上传/CRUD/分页查询)   │ 2. SSE (进度/LLM 流式)
┌───────▼──────────────────────────────▼─────────────────────┐
│         Nginx (上传缓冲 client_body_temp, 反代, SSE 不缓冲)   │
├────────────────────────────────────────────────────────────┤
│   API 服务 ×N (FastAPI, 多进程, 无状态, 可横向扩)             │
│   认证/双级RBAC · 团队/通知/审计 · 任务/聚合/LLM 触发              │
└───────┬──────────────────────────────┬─────────────────────┘
        │ 3. 任务入队 (Redis Stream)     │ 6. 订阅事件通道
┌───────▼──────────┐          ┌────────▼─────────────────────┐
│      Redis       │◄─────────┤   事件流                     │
│ · Stream 任务队列 │ 5.发布    │ · Pub/Sub 实时推送           │
│  (消费组+ACK+重试)│   进度    │ · Stream 事件留存(断线补发)   │
│ · 令牌黑名单/限流  │          │ · worker→API→浏览器          │
└───────┬──────────┘          └────────▲─────────────────────┘
        │ 4. 消费任务                   │
┌───────▼──────────────────────────────┴─────────────────────┐
│   分析 Worker ×N (独立进程, 可横向扩)                        │
│   解压校验 → 解析器插件(6种) → 事件入库 → 聚合统计            │
│   · 规则引擎匹配 → 按需 LLM 报告 (SSE 逐 token 流式)          │
│   · asyncio 驱动全流程, CPU 密集解析走 ProcessPoolExecutor    │
└───────┬────────────────────────────────────────────────────┘
        │
   PostgreSQL (用户/角色/权限/团队/任务/事件/规则/审计/
               指标时间分区/用户偏好) + 本地存储 (日志包)
```

**核心数据流**: 被动上传 → 入队即返回 task_id → Worker 并发异步分析 → 进度经 Redis 事件通道 → SSE 流式回推浏览器；LLM 报告按需触发（用户点击才调 LLM），同样走 SSE。

**本地文件浏览通道**（智能诊断「目录文件」，独立于上传分析链路，**不经过 Redis 与 Worker**）:

```
浏览器 (Vue3 SPA, EventSource)
  │  1. GET /api/fs/{roots,list,tree,read,raw}   (仅需登录态; /raw 支持 ?token=)
  ▼
API 服务 ── FS_ROOTS 白名单校验 (_resolve, 越界 403) ──► 后端所在主机文件系统
  ▲                                                          │ watchdog 递归监听
  └──── 2. SSE /api/fs/watch ◄───────────────────────────────┘
            created / modified / moved / deleted (handler 内 400ms 去重)
```

> 注意：该通道读取的是**后端进程所在主机**的文件系统，与「用户上传日志包」是两条独立路径。

## 3. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 后端框架 | FastAPI (Python 3.11+) | API 与 Worker 共用代码库，不同启动入口 |
| Web 服务器 | Uvicorn；Linux 可选 gunicorn 多 worker | API 无状态可多进程/多机 |
| ORM/迁移 | SQLAlchemy 2.0 (async)，当前 create_all | Alembic 迁移列入后续规划 |
| 数据库 | PostgreSQL | 元数据 + JSONB 阈值/审计详情；事件表支持 SQL 聚合（16 桶 spark） |
| 时序数据 | PostgreSQL 时间分区表 (起步) | 量大后 Linux 可平滑加 TimescaleDB 扩展 |
| 缓存/队列/事件 | Redis 5+ | Stream 任务队列 + Pub/Sub + Stream 事件留存 + 限流/黑名单 |
| 前端 | Vue 3 + TypeScript + Vite 6 + Pinia + Vue Router + ECharts | o-design CSS tokens 风格，无重型组件库；基于 witty-log-analyzer (MulanPSL-2.0) |
| 认证/权限 | JWT + 双级 RBAC | 平台级用户-角色-权限 + 团队级双角色；黑名单放 Redis |
| 任务调度 | APScheduler (AsyncIOScheduler) | 当前仅用于指标分区维护；巡检定时触发为预留骨架（未实现） |
| 智能分析 | 规则引擎 + 按需 LLM | 规则打底；LLM 报告用户点击才触发，未配置自动降级五段报告 |
| LLM 接入 | openai SDK (OpenAI 兼容 API) | 流式响应逐 token 经 SSE 转发 |
| 实时推送 | SSE (sse-starlette) | EventSource 无法带 header → `?token=` 查询参数认证；承载分析进度 / LLM 流式 / 目录变更三类事件 |
| 本地文件浏览 | watchdog 4+ (Observer) | 递归监听所选目录，监听线程经 `call_soon_threadsafe` 投递 asyncio 队列；只读访问 `FS_ROOTS` 白名单内路径 |

## 4. 模块设计

### 4.1 用户权限（双级 RBAC）

- **平台级**: 用户 - 角色 - 权限三级模型；admin 角色拥有全部权限（含 `rule:manage` 规则管理）
- **团队级**: 每个团队内两固定角色，权限对照表：
  - 管理员 (team_admin)：团队内全部权限（成员管理/审批/任务/审计等）；创建者即为管理员，二者权限已合一
  - 普通用户 (member)：查看团队任务，可执行解析与 LLM 分析
- `Team.owner_user_id` 仅保留为「创建人」元数据（用于标识创建人、默认审批人，且不可被移除），不构成独立权限角色
- 存量数据迁移：`team_members.role = 'owner'` 幂等合并为 `team_admin`（见 `core/schema_guard.py`）
- 13 个原子权限点（dashboard:view / team:* / task:* / audit:view 等），前端常量与后端镜像
- JWT 认证；刷新令牌；登出黑名单存 Redis
- 前端：路由守卫（menu 路由查平台权限）+ 页面内 `can(teamId, perm)`（团队资源按团队角色控制）+ `v-permission` 指令

### 4.2 团队协作

- 团队 (Team)：创建时自动将创建人加入为 team_admin 管理员；描述可改
- 成员 (TeamMember)：邀请（指定角色）/ 申请（member）→ 通知中心审批（同意/拒绝）
- 通知 (TeamNotice)：invite / apply 两类，登录后顶栏铃铛展示待处理
- 审计 (AuditLog)：团队级操作审计（创建任务/删除任务/成员变更等），admin 可看全部，普通管理员只看"我的团队 ∪ 自己"

### 4.3 故障诊断日志分析

```
上传 (文件 ≤512KB 前端切片预检 / 粘贴文本 ≤10MB 直传)
  → 入队 (Redis Stream), 立即返回 task_id
  → Worker 消费: 解析器插件 (用户指定类型, 6 种)
  → 结构化事件批量入库 (ParsedEventRecord)
  → SQL 聚合: 16 桶时间 spark + KPI + 分类/错误码/源IP TopN
  → 结果页: 五图表 (时序堆叠/分类占比/错误码/源IP) 
    + 原始日志服务端分页筛选 (级别/分类/错误码/IP/关键字)
    + 按需 LLM 报告 (SSE 流式, llm_section/llm_token/progress)
```

- 6 种解析器插件（注册制，新增格式不改核心代码）：
  linux_syslog / nginx_access / windows_event (JSON 导出) / redfish (JSON) / java_app / generic (兜底)
- 预检接口 `POST /tasks/precheck` 只传日志前 512KB 切片，返回可解析条数与样例，不落盘不入队
- 任务状态机 6 态：pending → running → done / failed / cancelled / interrupted；前端 running 时 2s 轮询

### 4.4 按需 LLM 报告

- 触发：结果页用户点击"生成 LLM 分析" → `POST /tasks/{id}/llm` → 返回 runId
- 流式：`GET /tasks/{id}/llm/events?run_id=&token=` SSE，事件类型 `llm_section`(标题) / `llm_token`(增量 token 或整行) / `progress` / `done` / `error`
- 降级：未配置 LLM 或调用失败 → 五段式规则报告构建器兜底（概览/致命错误/高频错误码/异常源IP/建议）
- Worker 内 LLM 调用 asyncio 并发上限 + 限流

### 4.5 智能巡检

- 上传日志包 (task_type=inspection) → 同一 Redis 队列 → Worker 执行
- 规则引擎优先 → LLM 总结；与诊断模块复用同一套规则引擎和 LLM 接入层
- 检查项插件化 (Checker 注册制)；定时巡检调度为**预留骨架、未实现**（`worker/scheduler.py` 的 `trigger_scheduled_inspections` 为占位空函数，尚无巡检计划表与配套界面，仅注册在调度器上）
- 巡检任务列表实时进度（2s 轮询 + 进度条）

### 4.5.1 智能巡检规则推荐（详情页）

对已完成的巡检任务，评估现有规则对该任务日志的覆盖完善程度，并推荐可新增的规则项。

```
详情页点击「智能巡检规则推荐」
  → POST /tasks/{id}/rule-suggestions  (返回 run_id, Redis 锁防重复触发)
  → 入队 (task_type=rule_suggest) → Worker: run_rule_suggest
  → 读取任务已解析事件 + 现有规则 → 评估覆盖度 → 生成建议项
  → 逐 token 发布 suggestion_token, 结束后发布 suggestion(items)/done
  → upsert rule_suggestions 表 (与任务一对一, 刷新/切页签可复看)
```

- 触发：`POST /tasks/{id}/rule-suggestions`（校验 done 巡检任务 + 任务可见性 + `task:llm` 权限；Redis 锁 `suggest:lock:{task_id}`；`INCR suggest:run:seq` 得 run_id）
- 流式：`GET /tasks/{id}/rule-suggestions/events?run_id=&token=`，通道 `{task_id}:suggest:{run_id}`，事件 `progress` / `suggestion_token` / `suggestion` / `done` / `error`
- 查询已存：`GET /tasks/{id}/rule-suggestions` 返回持久化结果（无则 404）
- 降级：未配置 LLM → 启发式评估（重解析任务日志，比对现有规则已覆盖行，对未覆盖的 error/critical 行按关键词模式表给出建议项），保证无 LLM 也可用
- 存储：`rule_suggestions` 表（`task_id` 唯一 FK，`assessment` 文本 + `items` JSONB 建议项 + `model` 来源标识）；**不写入 `reports.content`**
- 前端：详情页建议区块（流式评估文本 + 可编辑建议项列表 + 每项「接纳」→ 跳转规则管理页新增弹窗并预填）

### 4.6 规则管理（管理员）

- 规则为数据库实体，`rule:manage` 权限方可增删改，普通用户只读
- 规则结构：名称/描述、匹配类型（keyword/regex/threshold）、阈值 {metric, op, value}、级别 (info/warn/error/critical)、优先级、启用状态
- 校验：正则合法性 + 防灾难性回溯黑名单（嵌套量词等危险模式拒绝）
- 内容版本：`version` 为单条规则自身的内容版本，仅内容字段变更时 +1（启停与内容未变的提交都不产生新版本）
- 热加载：引擎每个任务执行时重新查库取启用规则，天然免重启；不依赖 `version` 做变更通知
- 变更审计 (RuleAuditLog)：操作人/动作/新旧内容；内置规则（`is_builtin`）与普通规则同等管理，`rule:manage` 权限者可停用或删除（删除前二次确认）

### 4.7 性能数据与图表

- **数据来源**: 日志解析提取的性能指标统一入时间分区表 (MetricPoint)
- **查询 API**: `POST /metrics/query` 按主机/指标/时间范围，`interval_seconds>0` 时服务端时间桶降采样；`/metrics/hosts`、`/metrics/names` 下拉动态化（不前端硬编码）
- **持久化策略**: 指标服务端存储 + 用户视图配置（主机/指标/范围）经 `/preferences/{key}` 落库
- **前端入口**: 本期不提供独立图表页，`/metrics` 路由重定向到性能分析页；指标查询能力仅由上述后端接口提供

### 4.7.1 性能离线分析（上传即解析）

面向"临时抓一段数据看一眼"的场景：用户上传采集文件，**请求内同步解析**并返回聚合结果，前端用 ECharts 渲染；**结果不落库**（与 4.7 的持久化图表互补）。

- **统一范式**: `modules/perf/` 下四个纯函数解析器，签名一致 `analyze(data: bytes, filename: str = "") -> dict`，返回前端可直接渲染的聚合结果：

  | 页签 | 解析器 | 输入 | 端点 |
  |---|---|---|---|
  | sar 性能分析 | `sar.py` | `LC_ALL=C sar` 文本（CPU / 内存 / 磁盘） | `POST /perf/sar/analyze` |
  | 网络抓包分析 | `netcap.py` | 抓包文本（源/目的 IP、协议、端口、长度） | `POST /perf/netcap/analyze` |
  | blktrace 分析 | `blktrace.py` | `blktrace` / `blkparse` 文本 | `POST /perf/blktrace/analyze` |
  | 中断计数变化 | `interrupts.py` | `/proc/interrupts` 多次快照 或 `sar -I` 输出（自动识别） | `POST /perf/interrupts/analyze` |

- **错误处理**: 解析失败抛 `PerfAnalysisError` 子类（如 `InterruptError`），API 层统一转 HTTP 400 并回传可读中文原因
- **上传限制**: 单文件 ≤100MB，`_read_upload` 统一读取，`_run(analyzer, file)` 统一包装为异步端点
- **中断计数变化（`interrupts.py`）**: 自动识别两类输入并归一化为同一输出结构（`format` / `unit` / `per_cpu` / `top` / `series` / `samples` / `warnings`）
  - `/proc/interrupts` 多次快照 → 相邻快照各中断源、各 CPU 的**计数变化量**（`unit=count`）；单快照时退化为展示累计计数并给出告警；计数回退（IRQ 重分配）按 0 处理并累计告警
  - `sar -I` 输出 → 各中断名的**中断速率**（`unit=per_s`）时序，自动跳过 `Average:` 行
- **前端**: `views/PerfView.vue` 以子页签（sar / 网络抓包 / blktrace / 中断计数变化）组织四个面板组件，上传即分析、可清空；`?tab=` 记忆当前页签

### 4.8 智能诊断（本地文件浏览工作台）

三栏工作台：左「目录文件」+ 底端「运行状态」停靠面板 / 中「文件阅读器」/ 右「会话对话」；只有左栏对接了后端真实数据。

- **接口**: `api/fs.py` 提供 `GET /fs/{roots,list,tree,read,raw}` + `GET /fs/watch`(SSE)。除 `/raw`、`/watch` 走 `get_current_user_or_query`（EventSource / `<img>` 无法带 Header，需支持 `?token=`）外均为 `get_current_user`；仅需登录态，不挂权限点
- **路径安全**: `_resolve()` 要求绝对路径且必须位于 `FS_ROOTS` 白名单内，越界 403；白名单为空时默认「用户主目录 + Windows 盘符」（`_roots()` 结果 `lru_cache`）
- **加载策略**: `/fs/tree` 一次性嵌套加载（受 `FS_TREE_MAX_DEPTH` / `FS_TREE_MAX_NODES` 预算约束）；单目录子项超过 `FS_EAGER_MAX_CHILDREN` 或超出预算时该节点**不带 `children`**，前端展开时再调 `/fs/list` 懒加载（`FS_LIST_MAX` 截断）。前端据此区分「已加载」（`children` 为数组，含空数组）与「未加载」（`children === undefined`）
- **实时刷新**: `/fs/watch` 用 watchdog `Observer` 递归监听所选目录；监听线程经 `loop.call_soon_threadsafe` 把变更投入 asyncio 队列，`EventSourceResponse` 以 15s ping 保活，handler 内做 400ms 去重（字典上限 512）；连接断开时在 `finally` 中 `observer.stop()` + `to_thread(observer.join)`
  - 前端收到事件后**定点刷新**受影响的已加载目录（`refreshDir` 带 snapshot，保留其下已展开子目录的既有内容），不整树重拉，保留展开状态
  - 已打开且无未保存编辑的文件自动重载最新内容；`deleted` 关闭对应页签，`moved` 改写页签 id / name / path
  - 重新选择目录（含重选同一目录）会释放上一次的勾选、展开态、待刷新队列与事件缓存
- **读取限制**: 文本超过 `FS_MAX_TEXT_MB` 只提示不加载；图片仅返回元信息，二进制走 `/fs/raw` 预览
- **前端**: `views/DiagnosisView.vue`（三栏与宽度联动、SSE 订阅、页签维护）+ `components/DiagnosisFileTree.vue`（目录树、勾选多选、拖拽、懒加载、事件定点刷新）+ `DiagnosisFileReader.vue`（多页签查看/编辑/保存/还原）+ `DiagnosisPathPicker.vue`（服务端路径选择弹窗）+ `DiagnosisInspector.vue`（运行状态）
- **当前边界**: 对话消息、工具调用、模型信息与 Todo 均为前端演示数据（`runAgent` 本地模拟），尚未接入真实 agent / 大模型；「目录文件」是唯一对接后端真实数据的部分

### 4.9 前端架构（o-design）

- 来源：witty-log-analyzer (MulanPSL-2.0) 整体替换，许可证随仓库携带 (`frontend/LICENSE-witty`)
- 约定：
  - 后端全 snake_case → http.ts 响应拦截深度驼峰化；`fields/sparks/threshold/pref_value` 为运行时数据字典键，跳过转换
  - 401 拦截 → refresh 重放（`_retried` 防循环），失败清 token 回登录
  - SSE 认证用 `?token=` 查询参数（EventSource 不能带 header）；`api/fs.ts` 的 `rawUrl()` / `watchUrl()` 自动附加 token
  - 列表类数据一律服务端分页（任务列表/原始日志/审计），防止大结果集拖垮前端
  - 页面：登录（账密+演示账号一键填充）/ 工作台 / 性能分析（sar / 网络抓包 / blktrace / 中断计数变化 4 子页签）/ 智能巡检（解析任务与巡检任务统一列表）/ 巡检详情 / 智能诊断（目录文件 / 文件阅读器 / 会话对话 三栏）/ 团队管理（直接展示当前团队详情：成员/规则集/大模型/用量/审计）；团队切换位于顶栏右侧，「其他团队」弹窗负责创建 / 进入 / 申请加入

### 4.10 任务可靠性

- Redis Stream 消费组: ACK 确认、pending 重投、Worker 崩溃任务不丢
- 任务 6 态状态机，元数据落 PostgreSQL，进程重启后 interrupted 可重新下发
- 取消：pending 直接置 cancelled；running 由 Worker 轮询 Redis 取消标记

## 5. 并发与扩展模型

| 层 | 模型 | 扩展方式 |
|---|---|---|
| API 层 | Uvicorn 多 worker (Linux 可 gunicorn) | 无状态，加机器即可 |
| Worker 层 | 多进程消费同一队列 | 线性加 Worker 进程/容器 |
| 日志解析 | CPU 密集 → ProcessPoolExecutor | 进程池大小按 CPU 核数调 |
| LLM 调用 | IO 密集 → asyncio + 并发上限 + 限流 | 调大并发上限/多 Worker |
| 事件推送 | Redis Pub/Sub 扇出 | API 层各自订阅，天然支持多实例 |
| 聚合统计 | 事件入库后 SQL/内存聚合 | 量大后可下沉物化视图/TimescaleDB |

**容量评估**: 1k 用户 / 100+ QPS 规模，2C API 实例 + 2~4 Worker + 单 Redis + 单 PostgreSQL 可从容支撑，增长时线性加 Worker。

## 9. 设计决策记录

| 决策 | 结论 | 理由 |
|---|---|---|
| 前后端分离 | 是 | Vue3 SPA + FastAPI REST |
| API 与分析解耦 | 是 | 100+ QPS 上传不能被分析拖慢，入队即返回 |
| 前端方案 | witty-log-analyzer o-design 整体替换 | 简约大气（符合客户要求）、无重型组件库、自带解析任务流；MulanPSL-2.0 宽松协议可商用 |
| 队列选型 | Redis Stream 消费组 | ACK/重投保可靠，避免引入 Kafka/RabbitMQ 重依赖 |
| 事件通道 | Redis Pub/Sub + Stream 留存 | 跨进程实时推送 + 断线补发 |
| 实时推送协议 | SSE 为主 | 单向流、自动重连、过代理友好；认证用 `?token=` 查询参数 |
| 智能方式 | 规则引擎优先 + **按需** LLM 总结 | 规则打底可离线可解释；LLM 用户点击才触发，省成本；未配置降级五段报告 |
| 命名契约 | 后端 snake_case，http.ts 统一深度驼峰化 | 不逐字段手写映射；数据字典键 (fields/sparks/threshold) 跳过 |
| 分页策略 | 列表/日志/审计一律服务端分页 | 大结果集不进前端内存；任务列表 spark 由 SQL 16 桶聚合直出 |
| 权限模型 | 平台 RBAC + 团队级双角色 | 规则管理等平台能力与团队资源隔离，团队内权限可独立委派 |
| 规则存储 | 数据库实体 + 内容版本 + 每任务重新加载 | 管理员界面 CRUD，Worker 不重启即生效 |
| 时序指标存储 | PostgreSQL 时间分区表 | 裸机需支持 Windows；量级起步够用，量大后 Linux 可平滑升级 TimescaleDB |
| 图表持久化 | 指标服务端存储 + 用户视图配置落库 | 刷新/切页签重新拉取即恢复，不依赖前端内存状态 |
| 日志格式扩展 | 解析器插件注册制 | 新格式不改核心代码；上传前 512KB 预检快速反馈 |
| 采集方式 | 被动上传 | 用户侧收集后上传，平台不主动 SSH |
| 规则推荐交互 | 按需 SSE 流式 + 任务绑定持久化，不写入报告 | 复用按需 LLM 范式；结果独立存储便于用户编辑；不污染巡检报告 |
| 规则推荐降级 | LLM 未配置 → 启发式评估 | 无 LLM 环境仍可给出未覆盖错误模式建议，能力不缺失 |
| 本地文件浏览 | 只读 + `FS_ROOTS` 白名单 + 绝对路径校验 | 直接看后端主机磁盘比「先上传再查看」即时；白名单 + 越界 403 防目录遍历，仅需登录态 |
| 目录加载策略 | 一次性嵌套加载优先，超阈值（子项数 / 深度 / 节点数）才懒加载 | 目录不大时一步到位体验最好；超大目录（如 node_modules）避免一次性拉爆响应 |
| 目录变更推送 | watchdog 递归监听 + 复用 SSE 通道，前端定点刷新 | 不引入 WebSocket 等新协议；只刷新受影响目录，保留展开态与勾选态，不整树重拉 |
| Celery | 不用 | 进程模型重，流式事件回传困难，Redis Stream + asyncio 足够 |
| 单库双入口 | API/Worker 共用代码库 | 部署形态不同，业务代码共享 |
| 演示数据 | 幂等种子 (SEED_DEMO_DATA 开关) | 5 演示账号 + 2 团队开箱可体验角色差异；生产一键关闭 |
