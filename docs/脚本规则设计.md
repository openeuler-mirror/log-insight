# 脚本规则（Script Rule）设计方案

> 状态：**设计评审稿，尚未实现**。当前线上规则仅支持 `regex` / `keyword` / `threshold` 三类，
> 见 [规则表设计.md](./规则表设计.md)。
>
> 目标：让规则在「命中执行」时可以运行一段 Python 脚本，用于关键字/正则/阈值难以表达的场景，
> 例如：单位时间窗口内同一条错误重复 N 次、日志时间戳回退（时钟漂移）、多行状态机
> （A 之后 M 秒内必须出现 B）、跨主机指标相关性判断等。

## 一、决策摘要

| 决策项 | 结论 |
|--------|------|
| 脚本存放 | **服务器脚本目录** `backend/rules_scripts/`，规则表只存相对路径 |
| 执行方式 | **独立子进程**运行，stdin/stdout 传 JSON，带超时 |
| 执行时机 | 每个任务在**日志解析完成后、指标入库前**，对所有启用脚本规则统一执行一次 |
| 契约 | 脚本暴露 `def check(ctx: dict) -> list[dict]`，由 runner 负责 JSON I/O 与异常兜底 |
| 失败影响 | 脚本自身报错/超时**不使任务失败**，仅记录该规则执行失败 |
| 维护者 | 需要 `rule:manage` 权限；等价于「受信人员可在服务器上执行代码」 |

## 二、数据模型变更

### 2.1 枚举扩展

```python
class MatchType(str, enum.Enum):
    regex = "regex"
    keyword = "keyword"
    threshold = "threshold"
    script = "script"        # 新增：执行 Python 脚本
```

### 2.2 `rules` 表新增字段

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `script_path` | String(256) | `""` | 相对脚本根目录的路径，仅 `script` 类型使用，如 `oom_burst.py` |
| `script_params` | JSONB | `{}` | 传给脚本的参数（脚本内通过 `ctx["rule"]["params"]` 读取），便于同一脚本复用 |
| `script_timeout` | Integer | `5` | 该规则超时秒数；`0` 表示使用全局默认 |

`pattern` / `threshold` 字段保持不动（`script` 类型下留空），避免破坏既有字段语义。

### 2.3 迁移要点

- PG 侧枚举类型名为 **`matchtype`**（SQLAlchemy 默认按枚举类名小写生成，已在基线 0001 确认）。
- `ALTER TYPE matchtype ADD VALUE 'script'` 在 PG 12+ 允许在事务中执行，但**同一事务内不能使用新值**。
  因此拆成两个迁移，避免踩坑：
  1. `0002_extend_matchtype_script.py`：仅 `ALTER TYPE ... ADD VALUE 'script'`
  2. `0003_add_script_rule_columns.py`：`ADD COLUMN script_path / script_params / script_timeout`
- 回滚：枚举值无法删除，降级脚本（`downgrade`）只回退列，枚举值保留（需在迁移中注明）。

## 三、脚本目录与命名规范

```
backend/
└── rules_scripts/              # 脚本根目录（随仓库版本管理）
    ├── README.md               # 契约说明 + 示例
    ├── oom_burst.py            # 示例：窗口内 OOM 重复次数
    ├── clock_skew.py           # 示例：日志时间戳回退检测
    └── _shared/                # 可选：脚本间共享的工具模块（被 import 时需注意隔离）
```

约定：

- 根目录由配置项 `RULE_SCRIPT_DIR`（默认 `./rules_scripts`，相对 backend）指定，纳入 `.gitignore` 白名单外的正式代码。
- 路径校验：`script_path` 必须是**相对路径**、后缀 `.py`、解析后的绝对路径必须位于根目录内（禁止 `..`、绝对路径、符号链接逃逸）。与 `safe_extract` 的路径穿越防护同思路。
- 目录内容由运维/开发用 IDE 或 git 维护；接口层提供 `GET /api/rules/scripts` 扫描列表供前端下拉选择，避免手写路径出错。

## 四、脚本接口契约

### 4.1 输入（runner → 脚本）

runner 通过 `ctx` 传入一个普通 dict：

```json
{
  "rule": {
    "id": 12,
    "name": "OOM 高频告警",
    "severity": "critical",
    "params": {"window_seconds": 60, "threshold": 3}
  },
  "task": {
    "id": "3f2b...",
    "task_type": "diagnosis",
    "server_type": "linux"
  },
  "entries": [
    {"line_no": 1, "raw": "Jan 1 ... Out of memory", "ts": "2026-10-10T12:00:00+08:00",
     "level": "ERROR", "component": "kernel", "file": "syslog", "fields": {}}
  ],
  "metrics": [
    {"host": "server-bj-01", "metric_name": "cpu.usage", "value": 91.2,
     "metric_time": "2026-10-10T12:00:00+00:00", "tags": {}}
  ],
  "file_stats": {"syslog": {"lines": 12000, "errors": 30, "warns": 12}},
  "meta": {"total_entries": 12000, "total_metrics": 576, "truncated": false}
}
```

- `entries` 字段对应 [LogEntry](../backend/app/modules/diagnosis/parsers/__init__.py) 的 `raw/timestamp/level/component/fields`，
  另加 `line_no`（全任务全局递增）与 `file`（来源文件名）便于定位。
- `metrics` 元素即 `ParseResult.metrics` 的原始结构。
- **上下文有上限**：`SCRIPT_MAX_ENTRIES`（默认 50000）/`SCRIPT_MAX_BYTES`（默认 16MB），
  超出时截断并置 `meta.truncated = true`；脚本应当据此降级（例如只做抽样统计）。

### 4.2 输出（脚本 → runner）

```json
{
  "findings": [
    {
      "line_no": 42,
      "matched_text": "Out of memory",
      "raw": "Jan 1 ... Out of memory",
      "message": "60 秒内第 4 次 OOM，疑似内存泄漏",
      "severity": "critical",
      "host": "server-bj-01"
    }
  ],
  "logs": ["窗口统计：4 次"]
}
```

| 键 | 必填 | 说明 |
|----|------|------|
| `findings` | 是 | 命中列表，可为空数组 |
| `findings[].line_no` | 否 | 关联日志行号，0 或省略表示与具体行无关（如指标类） |
| `findings[].matched_text` | 否 | 命中片段 |
| `findings[].raw` | 否 | 原始上下文，默认由 runner 按 `line_no` 回填 |
| `findings[].message` | 否 | 自定义说明，会覆盖 `raw` 展示 |
| `findings[].severity` | 否 | 覆盖规则自身级别（仍限四档枚举） |
| `logs` | 否 | 调试信息，写入任务事件流，不落报告 |

- 输出条数上限 `SCRIPT_MAX_FINDINGS`（默认 200），超出截断，防爆量撑爆报告。
- runner 对 `severity` / `line_no` 类型做校验，非法条目不采纳并计入 `logs`。

### 4.3 示例脚本

```python
"""oom_burst.py — 窗口内 OOM 重复次数超过阈值则告警.

规则配置示例: script_params = {"window_seconds": 60, "threshold": 3, "keyword": "Out of memory"}
"""


def check(ctx):
    params = ctx["rule"]["params"]
    window = int(params.get("window_seconds", 60))
    threshold = int(params.get("threshold", 3))
    keyword = params.get("keyword", "Out of memory")

    hits = [e for e in ctx["entries"] if keyword in e["raw"] and e.get("ts")]
    hits.sort(key=lambda e: e["ts"])

    findings, logs = [], []
    i = 0
    while i < len(hits):
        window_hits = [hits[i]]
        for e in hits[i + 1:]:
            if _seconds_between(hits[i]["ts"], e["ts"]) <= window:
                window_hits.append(e)
            else:
                break
        if len(window_hits) >= threshold:
            e = window_hits[-1]
            findings.append({
                "line_no": e["line_no"],
                "matched_text": keyword,
                "message": f"{window} 秒内第 {len(window_hits)} 次 OOM，疑似内存泄漏或超卖",
            })
            logs.append(f"{hits[i]['ts']} 起窗口命中 {len(window_hits)} 次")
            i += len(window_hits)
        else:
            i += 1
    return {"findings": findings, "logs": logs}


def _seconds_between(a, b):
    from datetime import datetime
    return (datetime.fromisoformat(b) - datetime.fromisoformat(a)).total_seconds()
```

## 五、执行模型

### 5.1 runner 入口

新增 `backend/app/modules/diagnosis/script_runner.py`，作为子进程的 `__main__`：

```python
"""子进程入口: 加载脚本模块 → 调用 check(ctx) → 输出 JSON 结果."""
# 伪代码, 实现时补齐
import importlib.util, json, sys
from pathlib import Path


def main() -> int:
    payload = json.load(sys.stdin)              # {script_path, ctx}
    script = _load_module(payload["script_path"])  # 由 root + 相对路径解析
    fn = getattr(script, "check", None)
    if not callable(fn):
        return _fail("脚本缺少 check(ctx) 入口函数")
    try:
        result = fn(payload["ctx"])
    except Exception as exc:                    # 脚本异常不外抛, 结构化返回
        return _fail(f"{type(exc).__name__}: {exc}")
    json.dump(_normalize(result), sys.stdout, ensure_ascii=False)
    return 0
```

Worker 侧调用：

```
sys.executable -I -m app.modules.diagnosis.script_runner
# cwd = backend/, env 最小化, stdin 写 JSON, 带 timeout
```

- `-I` 启用隔离模式（忽略环境变量与用户 site-packages）。
- 用 `asyncio.create_subprocess_exec` + `asyncio.wait_for` 实现超时；超时则 `kill` 进程。
- 退出码非 0 或 stdout 非法 JSON → 该规则标记执行失败。

### 5.2 并发与顺序

- **每个脚本规则一个子进程**，保证超时与崩溃互不影响（批量合并虽省启动开销，但无法做 per-rule 超时，故不采用）。
- 用 `asyncio.Semaphore(RULE_SCRIPT_CONCURRENCY)`（默认 4）限制并发，结果按规则 `priority, id` 顺序合并进 `all_findings`。
- 单次进程启动约几十毫秒；脚本规则数量通常很少（<10），开销可接受。

### 5.3 资源限制（跨平台差异，需如实说明）

| 平台 | 措施 |
|------|------|
| Linux（生产） | 子进程 `preexec_fn` 中 `resource.setrlimit` 限制 `RLIMIT_AS`（内存）、`RLIMIT_CPU`（CPU 时间）、`RLIMIT_NOFILE` |
| Windows（本机开发） | 无 `resource` 模块，**仅有超时保护**；内存/CPU 不限。故脚本规则不建议在本机做压测 |

## 六、安全边界

必须明确的风险与缓解（本方案不提供强沙箱）：

1. **等价于任意代码执行**：脚本以 Worker 相同系统用户身份运行，可读写其可访问的文件、发起网络请求。
   - 缓解：只有 `rule:manage` 权限者可配置规则；脚本目录纳入代码评审；文档明确信任模型。
2. **路径穿越**：`script_path` 严格校验（相对路径 + 后缀 + 解析后必须在根目录内），杜绝 `/etc/passwd`、`../../` 等。
3. **拒绝服务**：超时 + 输出条数上限 + 输入上下文上限 + 并发信号量。超时不外溢到任务。
4. **供应链**：脚本可 `import` 任意三方库（继承 backend 环境）。如需更严，可后续引入受限解释器/容器执行（列为演进项，见第九节）。
5. **审计**：脚本规则的增删改同样写入 `rule_audit_logs`（`detail` 记录规则字段变更）。
6. **脚本文件与规则版本解耦**：规则 `version` 只反映规则记录的内容变更（且仅内容字段变化才 +1），脚本内容改动不影响 `version`。
   **评审结论：不加** `script_hash`，不做一致性校验。因为脚本每次执行都从磁盘重新加载，
   内容改动天然下次任务即生效；仅需注意「规则记录无变更」不等于「行为无变更」。

## 八、错误处理与可观测性

- 脚本执行失败（超时/非零退出/JSON 非法/缺 `check`）：
  - **不使任务失败**，任务继续走到报告；
  - 在任务事件流发布 `warning`，内容含规则名 + 失败原因；
  - 报告中 `content.script_errors = [{"rule_id", "rule_name", "error"}]` 供前端展示；
  - Worker 日志按 `ERROR` 打印完整 stderr（截断 2000 字符）。
- 脚本 `logs` 输出：以 `progress`/`log` 事件推送到前端，不写入报告正文。
- 建议在报告 `content` 中记录每条脚本规则的耗时，便于发现慢规则。

## 十、已确认决策（评审结论）

1. **脚本变更感知**：**不做**。不新增 `script_hash` 字段，不做一致性校验；脚本每次执行重新读盘，改动天然生效。
2. **内置示例脚本**：设 `is_builtin=true`（标记来源，可停用、`rule:manage` 权限者可删除），`script_path` 指向随仓库发布的脚本。
3. **`line_no` 语义**：**不做** `entries_by_file`。保持「全局递增 `line_no` + `file` 字段」，
   脚本如需按文件分组可自行依据 `file` 字段分组。
4. **脚本级依赖声明**：**不做**。脚本直接使用 backend 环境已安装的依赖。
5. **演进项**：**不做**。容器化/受限解释器、脚本在线编辑（存库）、脚本单测框架均不纳入本期。

> 以上为最终基线，实现时不再引入额外字段与机制。
