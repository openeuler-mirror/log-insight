# 日志诊断工作流

## 1. 明确问题

从用户描述中提取四件事，缺什么就先问（最多问一轮）：

- 现象：什么不可用、报什么错、影响范围。
- 时间：故障开始时间、是否仍在持续、是否周期性。
- 对象：主机 / 服务 / 进程 / 路径 / 请求。
- 已有材料：本次工作区里有哪些日志，覆盖什么时间段。

## 2. 先看全局，再钻细节

按以下顺序取证，拿到足够证据就停止，不要为了"看全"而通读大文件：

1. 列出 `uploads/` 下文件，确认大小与时间范围。
2. 按错误级别和关键字检索：`error`、`fail`、`timeout`、`killed`、`oom`、
   `panic`、`segfault`、`I/O error`、`refused`、`unreachable`、`5xx`。
3. 对命中行读取前后各 5～10 行，恢复上下文。
4. 需要时再按时间窗口聚合，确认故障起止与峰值。

大文件优先用 `grep` / `rg` 定位行号，再读取局部，不要一次读入整个文件。

## 3. 关联证据

对每条候选原因，至少找到两类互相独立的证据，例如：

- 内核日志的 OOM 记录 + 应用日志的重启记录；
- nginx 的 upstream timeout + 后端慢请求日志；
- 磁盘 I/O error + 文件系统只读 / 进程阻塞。

只有一类证据时，标为「疑似」。

## 4. 常见方向

- 内存：OOM killer、cgroup 限额、泄漏、缓存占用。
- CPU：单进程打满、锁竞争、正则回溯、中断软中断分布。
- 磁盘：I/O error、await/util 偏高、inode 耗尽、只读挂载。
- 网络：连接拒绝/超时、SYN 洪水、DNS、端口监听、丢包。
- 服务：systemd 重启循环、启动失败、依赖未就绪、配置错误。
- 时间：时钟漂移、时区错乱、证书过期。
- 安全：暴力破解、权限拒绝、SELinux 拦截。

需要更细的排查路径时加载 `linux-triage` 技能。

## 5. 给出结论

严格按下面的结构回答：

```markdown
结论：<一句话根因>

证据：
- <文件>:<行号> <时间> <原文摘录>
- ...

处置建议：
1. <动作>（预期效果）
2. ...

还需要：<缺少的材料，没有则省略>
```

如果证据不足，明确写「当前日志不足以确认根因」，并给出下一步需要采集的内容。
